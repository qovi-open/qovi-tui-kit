Qovi TuI — authentifier une application sans interface

Un script, un service, un backend, un objet connecté… même sans écran, il peut exiger une authentification forte, validée sur le mobile de la personne. Linux · .deb C Python Windows · .msi

L'idée

Votre application ne sait rien de la cryptographie ni de Qovi. Elle demande simplement : « cette personne confirme-t-elle ? » La personne reçoit la demande sur son mobile, avec la raison que vous indiquez, et accepte ou refuse. Votre application reçoit le verdict, confirmé par Qovi.

Deux rôles distincts

  • Le service qovi-tuid tourne en permanence sur la machine. Il détient la clé privée de votre site, dialogue avec Qovi et n'écoute que sur la machine elle-même (127.0.0.1).
  • Le client qovi-tui est appelé par votre application. Il ne connaît aucune clé : il transmet l'adresse à authentifier et rend le verdict.
La clé privée n'est lisible que par le service. Votre application, vos scripts et vos utilisateurs n'y ont jamais accès.

Ce qu'il vous faut

1
Une adresse e-mail dédiée au site, par exemple ch.qovi@votredomaine.com (le préfixe ch.qovi évite tout conflit), sur laquelle l'app Qovi est appairée.
2
Connectez-vous sur qovi.ch avec cette adresse : la clé privée de votre site (64 caractères hexadécimaux) y est affichée, prête à copier. Gardez-la dans votre trousseau ; elle ne se transmet à personne.
3
Les personnes à authentifier ont l'app Qovi sur leur mobile, appairée à leur adresse.

Installer

Debian 12 ou 13, Ubuntu 22.04 ou plus récent (amd64)

1
Téléchargez le paquet qovi-tui.deb ; il arrive en général dans le dossier Téléchargements.
Ce guide peut être lu hors ligne : double-cliquez sur le fichier qovi-tui-kit-README.html dans votre explorateur de fichiers (le panneau « Téléchargements » de Firefox n'affiche que ce que Firefox a lui-même téléchargé).
2
Installez-le dans un terminal. Votre mot de passe vous est demandé. 
cd ~/Téléchargements
sudo apt install ./qovi-tui.deb
Le fichier ne se lance pas (./qovi-tui.deb seul provoque une erreur) : il s'installe avec la commande ci-dessus. Le ./ placé après apt install indique un fichier du dossier courant. Inutile de changer ses droits.
Une note peut s'afficher : « N: Le téléchargement est effectué hors bac à sable en tant que root, car le fichier … n'est pas accessible par l'utilisateur « _apt ». … (13: Permission non accordée) ». Elle est sans conséquence : l'installation continue normalement.
L'installation crée l'utilisateur système qovi-tui, le fichier /etc/qovi-tui.conf (lisible par lui seul) et le service qovi-tui, qui attend votre clé.
3
Renseignez la clé privée du site, de l'une de ces deux façons.

a) En la collant — tapez la commande seule :

sudo qovi-tui-setkey

Deux questions se suivent : d'abord le mot de passe de votre compte (celui de sudo), ensuite seulement la clé. À la seconde question, collez la clé (dans un terminal : Ctrl+Maj+V, ou sélection puis clic du milieu) et appuyez sur Entrée. Rien ne s'affiche, c'est voulu.

b) Depuis un fichier — recommandé si le copier-coller est capricieux (bureau à distance…) : enregistrez la clé seule dans un fichier, puis :

sudo qovi-tui-setkey --file ~/ma-cle.txt

L'outil lit la clé, l'enregistre, puis propose d'effacer le fichier : répondez o. Une clé privée ne doit pas rester dans un fichier ordinaire.

L'outil affiche à la fin le serveur Qovi utilisé : la production (https://qovi.ch/RST) par défaut. Pour le serveur de test de Qovi, ajoutez --api https://tst.qovi.ch/RST à la commande : une clé de test est refusée par la production.

Les espaces et retours à la ligne en trop sont ignorés. Une clé incomplète est refusée sans rien modifier. En cas de succès, l'outil démarre le service et affiche l'identifiant public du site, qui permet de vérifier quelle clé est en place sans rien dévoiler.

4
Vérifiez que le service tourne : 
systemctl is-active qovi-tui
La réponse doit être active. Si elle est inactive, la clé n'est pas encore en place : refaites l'étape 3.
5
Premier essai, téléphone en main : 
qovi-tui login --edr ch.qovi@votredomaine.com --subj "Mon premier essai"
Le mobile affiche la demande avec la raison ; vous acceptez ; le terminal affiche OK authentifie ….
C'est tout. Le service redémarre tout seul avec la machine.

Windows 10 / 11 (64 bits)

1
Téléchargez qovi-tui.msi et double-cliquez dessus. Windows demande l'autorisation d'installer (compte administrateur).
Le paquet n'est pas encore signé : si Windows SmartScreen affiche « Windows a protégé votre ordinateur », cliquez sur Informations complémentaires puis Exécuter quand même.
L'assistant affiche la licence : cochez J'accepte, cliquez sur Installer et attendez l'écran final, puis Terminer.
L'installation place qovi-tuid.exe (le service) et qovi-tui.exe (le client) dans C:\Program Files\Qovi\TuI, ajoute ce dossier au PATH et crée le service Windows Qovi TuI, qui attend votre clé.
2
Ouvrez une console administrateur : clic droit sur le bouton Démarrer, puis Terminal (administrateur). Ouvrez-la après l'installation, pour qu'elle connaisse le nouveau PATH.
3
Renseignez la clé privée du site, de l'une de ces deux façons : 
qovi-tuid setkey
collez la clé quand elle est demandée (clic droit ou Ctrl+V) puis Entrée — rien ne s'affiche, c'est voulu ; ou, depuis un fichier contenant la clé seule : 
qovi-tuid setkey --file C:\Users\vous\ma-cle.txt
l'outil propose ensuite d'effacer le fichier : répondez o.
La clé est enregistrée dans C:\ProgramData\Qovi\TuI\qovi-tui.conf, lisible seulement par le service, SYSTEM et les administrateurs. L'outil affiche l'identifiant public du site et le serveur Qovi utilisé, puis démarre le service. Sans --api, c'est la production (https://qovi.ch/RST).
Clé d'un site du serveur de TEST de Qovi ? Ajoutez --api https://tst.qovi.ch/RST : 
qovi-tuid setkey --api https://tst.qovi.ch/RST
Sinon l'essai répond « clé du site refusée par Qovi (serveur https://qovi.ch/RST, production) » : refaites simplement setkey avec --api.
4
Vérifiez que le service tourne (dans n'importe quelle console) : 
sc query QoviTuI
La ligne STATE doit indiquer RUNNING. Sinon, la clé n'est pas encore en place : refaites l'étape 3.
5
Premier essai, dans une console ordinaire, téléphone en main : 
qovi-tui login --edr ch.qovi@votredomaine.com --subj "Mon premier essai"
C'est tout. Le service démarre tout seul avec Windows.

⚙️ C (Linux)

sudo apt install build-essential libssl-dev
cd c
make            # qovi-tuid (service) et qovi-tui (client)
make test       # tests sans réseau ni téléphone (python3-cryptography, openssl)
make deb        # le même paquet que ci-dessus, dans dist/

Pour un essai sans installation, le service lit la clé dans la variable QOVI_PRV_US ou dans un fichier de configuration (même format que /etc/qovi-tui.conf, voir qovi-tui.conf.example), puis :

./qovi-tuid ma.conf ch.qovi@votredomaine.com "Essai direct"

🐍 Python (Linux, Windows)

Service de référence, lisible en quelques pages : une demande à la fois. Pour la production, préférez le paquet.

sudo apt install python3-cryptography      # ailleurs : pip install cryptography
cd python
python3 _tuip.py                           # service sur 127.0.0.1:7777
python3 _tuip.py ch.qovi@votredomaine.com "Essai direct"

La clé est lue dans QOVI_PRV_US ou dans /etc/qovi-tui.conf (ligne prv_us = …, fichier en chmod 600) ; elle n'est jamais écrite dans le code.

Utiliser TuI depuis votre application

Le plus simple : appeler le client qovi-tui, dans n'importe quel langage.

qovi-tui login --edr <adresse> [--subj <raison>] [--json] [--port <port>]
Code de sortieSignification
0accepté — l'identité est confirmée par Qovi
1refusé (par la personne, ou adresse inconnue)
2pas de vote dans le délai (130 s au plus)
3erreur (service arrêté, réseau, configuration…)
4mauvaise utilisation de la commande

Avec --json, une ligne JSON par événement, pour suivre l'attente en direct :

{"ev":"sent"}                                    # demande partie
{"ev":"wait","t":"demande envoyee au mobile…"}   # sur le mobile
{"ev":"go","edr":"ch.qovi@votredomaine.com","t":"accepte"}
# ou une ligne finale : {"ev":"ko",…}  {"ev":"timeout",…}  {"ev":"error",…}

Exemple en shell

if qovi-tui login --edr "$ADRESSE" --subj "Ouverture de la porte"; then
    echo "autorisé"
else
    echo "refusé"
fi

Exemple en Python

import json, subprocess
p = subprocess.run(["qovi-tui", "login", "--edr", adresse, "--subj", raison, "--json"],
                   capture_output=True, text=True, timeout=140)
fin = json.loads(p.stdout.splitlines()[-1])
autorise = (p.returncode == 0 and fin["ev"] == "go")

Sans le client : le socket local

Toute application peut aussi parler directement au service, sur 127.0.0.1:7777, en envoyant une ligne :

  • adresse|raison → une ligne en retour : Go … ou Ko … ;
  • {"edr":"…","subj":"…"} → les lignes JSON ci-dessus.

Le script tui du kit (5 lignes de shell) en est un exemple.

Réglages facultatifs dans /etc/qovi-tui.conf (Windows : C:\ProgramData\Qovi\TuI\qovi-tui.conf) : port (7777), timeout (attente du vote, 10 à 130 s), log_file. Après modification : sudo systemctl restart qovi-tui (Windows : sc stop QoviTuI puis sc start QoviTuI, en administrateur).

Ce que TuI fait en coulisses

votre app ─► qovi-tui ─► qovi-tuid (127.0.0.1) │ 1. SiT_1_Edr : requête SIGNÉE (HTTPS) ─► jeton de transaction │ 2. CH4 : TLS + AES-256-GCM ─► demande sur le mobile, vote │ 3. SiT_3_End : requête SIGNÉE ─► Qovi CONFIRME le verdict votre app ◄─ go / ko ◄────────┘

Sécurité

  • La clé privée ne quitte jamais la machine : elle sert seulement à signer les requêtes et à vérifier les réponses de Qovi (HMAC-SHA256). Une réponse non signée ou falsifiée est rejetée.
  • Tous les échanges passent en TLS, certificat et nom du serveur vérifiés. Le canal du vote est en plus chiffré et authentifié (AES-256-GCM) ; le jeton de transaction n'y circule jamais.
  • Le verdict n'est « accepté » qu'après confirmation par Qovi (à usage unique) et pour la même adresse que celle demandée.
  • Le service n'écoute que sur 127.0.0.1, limite à 5 demandes simultanées et 1 par adresse, coupe les clients lents et ne journalise ni clé ni jeton.
  • Il tourne sous un utilisateur dédié, sans privilège : sous Linux avec un système de fichiers en lecture seule (durcissement systemd) et une configuration en 0600 ; sous Windows sous le compte virtuel NT SERVICE\QoviTuI, la configuration n'étant lisible que par lui, SYSTEM et les administrateurs.
  • Prérequis : une horloge à l'heure (NTP), à ± 60 secondes.
  • Une faille ? Écrivez à security@qovi.ch.
